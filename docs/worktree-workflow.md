# Worktree 開発ワークフロー設計

job-hunt-agent の「常時 worktree 開発」と並列開発の設計をまとめたドキュメント。
BeerSalon で確立したワークフローを Go プロジェクト向けに移植したもの。

---

## 0. 撤退路（`--no-worktree`）と費用対効果の前提

このワークフローは「常時 worktree」を既定とする。

**Go では worktree の固定オーバーヘッドがほぼゼロ**である点が重要:

- モジュールキャッシュ（`GOMODCACHE`）はマシン全体で共有されるため、
  worktree ごとの依存インストール（`pnpm install` 相当）が **不要**。
- ビルドキャッシュ（`GOCACHE`）も共有されるため、初回ビルドも大半がキャッシュヒットする。

そのため、Node/pnpm 系プロジェクト（BeerSalon）で問題になった「worktree 作成のたびに
数十秒〜数分の install が走る」というコストが、このリポジトリでは発生しない。
**常時 worktree 運用が素直に成立する。**

**撤退路**: それでも `/impl <Issue> --no-worktree` で従来の checkout 方式に切り替えられる。
コードを巻き戻す必要はない。

## 1. 基本思想

**並列・単独を問わず、開発は必ず git worktree で行う（既定）。develop メインのチェックアウトは「司令塔」専用とし、実装で汚さない。**

- `develop` メインチェックアウト = 司令塔（指揮所）。常に clean に保つ。
- 各タスクの実装は `.claude/worktrees/<branch>` で行う。
- これにより「単独開発」も「並列開発」もフローの入口が統一される。

### なぜこの形か（Why）

- 司令塔の `git status` がいつ見ても綺麗で、ブランチ取り違え・stash 地獄が起きない。
- worktree はファイルを物理的に分離するので、複数タスクのコードが混ざらない。

### 重要な前提：worktree が隔離するのは「ファイルだけ」

worktree は作業ディレクトリのファイルを分離するが、**ランタイムは分離しない**。
現時点の job-hunt-agent は共有ランタイム基盤（DB・固定ポートで待ち受けるサーバー等）を持たないため、
この制約は顕在化していない。**将来 DB や固定ポートを導入した時点で §2 が効き始める。**

---

## 2. 共有リソース制約（将来 DB・固定ポートを導入した場合）

> **現時点では該当なし。** 以下は、外部の共有リソースを導入した時点で有効になる設計方針。
> 導入時にこの節を「現行の制約」に昇格させ、`/impl` 1-3-1 の記述も合わせて更新すること。

### ① スキーマ変更は直列ロック

全 worktree が同一物理DBを共有する構成にした場合、スキーマ変更（マイグレーション追加）を
2つの worktree で同時に行うと互いに壊し合う。

**対策**: スキーマ変更を含むタスクは司令塔が直列順序を担保する。

### ② サーバーのポートはプールから払い出し

複数 worktree で同時にサーバーを起動するとポートが衝突する。

**対策**: ポートをプールから払い出す（例: 8080, 8180, 8280）。
環境変数でポートを注入できる設計にしておくこと（ハードコードしない）。

### ③ 統合テスト（IT）は共有リソースに触る

`-tags=integration` のテストが実DB・実サーバーに触る場合、複数 worktree で同時実行すると
競合して非決定的になる。

**対策**: §3 の直列キューへ。

## 3. テストの分類と並列可否

| フェーズ | コマンド | 共有リソース依存 | 並列可否 |
|---|---|---|---|
| 実装 + **UT** | `go test ./...`（外部依存はフェイク） | 触らない | **並列OK**（worktree 内で完結） |
| **IT（統合テスト）** | `go test -tags=integration ./...` | 現時点: 触らない / 将来: 触る可能性 | 現時点: **並列OK** / 将来: **直列キュー** |

**現時点では IT も worktree 内で実行してよい。** 共有 DB・固定ポートを導入した時点で、
以下の直列キュー運用に切り替える:

```
worktree-A (実装サブエージェント) ──「実装＋UT完了。IT要求」──┐
worktree-B (実装サブエージェント) ──「実装＋UT完了。IT要求」──┤
                                                           ▼
                                   ┌──────────────────────────────┐
                                   │ 司令塔 (developメイン)          │
                                   │ IT実行キューを管理（直列消化）   │
                                   │  ① qa-engineer起動→A検証        │
                                   │  ② qa-engineer起動→B検証        │
                                   └──────────────────────────────┘
```

### なぜ qa-engineer に任せるか（実行主体）

- 実装者（go-engineer）の自己テストでは独立性が担保できない。品質ゲートは別エージェントに分担させる。
- 司令塔が直接テストを回すと、テストログや試行錯誤が司令塔のコンテキスト窓に流れ込んで肥大化する。
  実行を qa-engineer に切り出すことで司令塔は「キュー管理」に専念できる。

### 厳守事項（共有リソース導入後）

- **`qa-engineer` を複数同時に起動して IT を並列で回してはいけない**（共有リソース競合で
  結果が非決定的になる）。司令塔は必ず「1体起動 → 完了 → 次」を守る。

## 4. worktree 作成の正確な手順

### develop 起点で切る（必須）

```
git fetch origin develop
git worktree add .claude/worktrees/<branch> origin/develop -b <branch>
```

- ブランチ命名は `/impl` と同じ規則: `feature/<issue番号>-<英語スラッグ>` 等。
- **なぜ生の `git worktree add` か**: Claude Code の Agent `isolation: "worktree"` /
  `--worktree` は既定ベースが `origin/HEAD`(=main) で、`origin/develop` を直接指定できない。
  ベースを明示できる生コマンドを使う。

### worktree の初期化

Go ではモジュールキャッシュが共有されるため、**依存インストールは不要**。やることは以下だけ:

- **環境ファイルのコピー**: `.env` 等が存在する場合のみ、新 worktree へコピーする（git 管理外のため）。
- **（任意）ビルドキャッシュの予熱**: `go build ./...`

### 後片付け

- PR作成完了後、`git worktree remove .claude/worktrees/<branch>`。
- 未コミット変更が残る場合は撤去せずユーザーに報告。
- `.gitignore` に `.claude/worktrees/` を登録済み（メインチェックアウトを汚さない）。

---

## 5. アンチパターン（やってはいけない）

- 司令塔（develop メイン）で直接実装してツリーを汚す
- worktree を撤去せずに放置し、ブランチ削除が失敗する状態を作る
- ポートを動的に好き勝手ずらす（環境変数で注入する設計にしておく）
- 共有リソース導入後に、複数 worktree で同時に IT を回す

---

## 6. 既存資産への影響

| 対象 | 影響 |
|---|---|
| `/impl` スキル | worktree 起点。1タスク=1worktree の実装フロー本体 |
| `/merge` スキル | マージ前に worktree が撤去済みであることを前提とする（残っていれば先に remove） |
| `.gitignore` | `.claude/worktrees/` を登録済み |
