## 開発環境トラブルのトリアージ

引数: `$ARGUMENTS`（症状の説明。省略時はヒアリングを行う）

### 症状のヒアリング

ユーザーの発言から症状カテゴリを推定できない場合、以下の2軸で質問する:

**1. 何をしようとしましたか？**
- ビルドしようとした / 型チェックを通そうとした
- 依存パッケージを追加・更新しようとした
- テストを実行しようとした
- Lint を通そうとした
- アプリを起動しようとした
- gitコマンドを実行しようとした

**2. 何が起きましたか？**（エラーメッセージ、具体的な症状）

### 振り分けルール

| 症状カテゴリ | 案内先 |
|---|---|
| ビルドが通らない・コンパイルエラー | `/build-problem` を使ってください |
| モジュール依存が解決できない・バージョン衝突 | `/build-problem` を使ってください |
| gitコマンドが重い・結果が返ってこない | `/git-problem` を使ってください |
| テストが落ちる・ハングする・flaky | 直接診断を実行（下記フォールバック参照） |
| Lint / vet が落ちる | 直接診断を実行（下記フォールバック参照） |
| ツールチェーンが見つからない・バージョン不一致 | 直接診断を実行（下記フォールバック参照） |
| 実行時に落ちる・panic する | 直接診断を実行（下記フォールバック参照） |

### 複合問題の優先順位

問題が複数カテゴリにまたがる場合、以下の順で基盤的な問題から解決する:

1. ツールチェーン — `go` が動かないと全てに影響
2. モジュール依存 — 依存が壊れているとビルド・テストが全滅する
3. ビルド・コンパイル — ビルドブロッカーは他の作業を止める
4. テスト
5. Lint / vet
6. 実行時の不具合
7. Git

### フォールバック: 直接診断

専門スキルが存在しないカテゴリの場合、dev-doctor エージェント本体の「汎用診断フレームワーク」に従って直接診断を行う。ユーザーに「スキルが未作成です」等のメッセージは表示せず、シームレスに対応すること。

汎用診断フレームワーク:
1. **環境基盤の健全性確認** — Go ツールチェーン、golangci-lint、`go.mod`/`go.sum`、環境変数
2. **カテゴリ固有の診断** — 症状に応じた具体的チェック
3. **修復提案** — 重要度付き問題リスト + 優先順位付きコマンド

### 禁止事項

- `run_in_background: true` の使用
- ユーザー承認なしでの破壊的操作の実行（`go clean -modcache` 等）
- 原因を特定せずに「とりあえずキャッシュを消す」提案をすること
- `.env` ファイルの直接編集（ユーザーに手順を案内する）
